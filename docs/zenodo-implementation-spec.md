## Current State

### Existing Release Pipeline

The release is driven by `release-it` (v19.2.4), invoked via:

```bash
pnpm run release          # → dotenv -e .env -- release-it
```

**`.release-it.ts` orchestration:**

1. **`after:bump` hooks** (runs after version bump in `package.json`):
   - `pnpm run generate:figures` — rebuilds all figures via `bash scripts/figures/build.sh`
   - `pnpm exec tsx scripts/build.ts ${version}` — full release build:
     - Cleans old versions from `build/`
     - Syncs citation metadata (`syncCitationMetadata`): updates `CITATION.cff` version + date, generates `.zenodo.json` from CFF, validates both against JSON schemas
     - Compiles LaTeX PDF → `build/document-v${version}.pdf`
     - Generates `checksums.txt`

2. **Plugins:**
   - `@release-it/bumper`: bumps version in `package.json`, `CITATION.cff`, and `pyproject.toml`
   - `@release-it/conventional-changelog`: generates `CHANGELOG.md`

3. **Git operations:**
   - Commit: `chore: release v${version}`
   - Tag: `v${version}`
   - Push to `main`
   - Add untracked files (picks up `build/`, `.zenodo.json`, `CHANGELOG.md`, updated `CITATION.cff`)

4. **GitHub release:**
   - Name: `v${version}`
   - Assets: `build/document-v*.pdf`, `checksums.txt`

### Generated Metadata Files

The build pipeline already generates both files that Zenodo needs:

| File | Source | Content |
|------|--------|---------|
| `CITATION.cff` | Updated by `@release-it/bumper` + `citation.ts` sync | Version, date, references, DOI identifiers |
| `.zenodo.json` | Generated by `citation.ts` from CFF | Full Zenodo deposition metadata (creators, keywords, references, related_identifiers, etc.) |

**Key insight**: The `.zenodo.json` is already comprehensive and ready for Zenodo ingestion — it contains title, description, version, publication_date, creators (with ORCIDs), keywords, upload_type, access_right, license, references, and related_identifiers.

## Option A: megasanjay/upload-to-zenodo

### Source Code Analysis

The action (`megasanjay/upload-to-zenodo@v2`) does the following:

1. **Creates context** from GitHub release event — extracts `tag_name`, `assets`, `repository`
2. **Downloads metadata files** from the GitHub repo (`CITATION.cff`, `.zenodo.json`, `codemeta.json`)
3. **Downloads release assets** from the GitHub release
4. **Creates a new Zenodo deposition version** via `POST /api/deposit/depositions/{id}/actions/newversion`
5. **Deletes all files** from the new draft deposition
6. **Updates metadata files** (CITATION.cff version/DOI, .zenodo.json version) if `update_metadata_files: true`
7. **Commits updated metadata** back to GitHub via API (this is the critical side effect)
8. **Re-downloads source zipball** (to get the commit with updated metadata)
9. **Uploads source zipball + all release assets** to the Zenodo draft
10. **Updates Zenodo metadata** with the `title` from `.zenodo.json` (but NOT the full metadata — only title)
11. **Optionally publishes** the deposition

### Exact YAML Workflow

```yaml
name: Upload to Zenodo

on:
  release:
    types: [published]

permissions:
  contents: write

jobs:
  upload-to-zenodo:
    runs-on: ubuntu-latest
    steps:
      - name: Upload to Zenodo
        uses: megasanjay/upload-to-zenodo@v2
        with:
          zenodo_token: ${{ secrets.ZENODO_TOKEN }}
          zenodo_deposition_id: ${{ secrets.ZENODO_DEPOSITION_ID }}
          zenodo_publish: "true"
          # Disable automatic metadata file updates — we handle this ourselves
          update_metadata_files: "false"
          # We have .zenodo.json but NOT codemeta.json or zenodo_json input
          # Setting these to false prevents the action from looking for them
          codemeta_json: "false"
          citation_cff: "false"
          zenodo_json: "false"
          docs_compatibility_json: "false"
```

### How It Interacts with release-it

**The action runs AFTER release-it**, triggered by the `release: published` event.

| Step | Who | What |
|------|-----|------|
| 1 | release-it | Version bump in `package.json`, `CITATION.cff`, `pyproject.toml` |
| 2 | release-it hooks | `generate:figures` + `build.ts` (compiles PDF, syncs `.zenodo.json`) |
| 3 | release-it | Git commit, tag, push, GitHub release with PDF + checksums |
| 4 | GH Action | Triggered by `release: published` event |
| 5 | GH Action | Creates new Zenodo deposition version, uploads source zip + release assets |

**Critical interaction**: If `update_metadata_files: false`, the action does NOT push any commits back to the repo. It only creates a new Zenodo deposition version and uploads files. This avoids the problematic loop where the action commits metadata changes that could trigger another workflow.

If `update_metadata_files: true` (default), the action commits updated CITATION.cff/.zenodo.json back to GitHub, which means:
- The GitHub release assets won't contain the updated metadata files
- It creates extra commits on the branch
- It could potentially trigger infinite loops with webhooks

**Recommendation**: Set `update_metadata_files: "false"` since our `build.ts` already handles all metadata updates before the release.

### Required Secrets

| Secret | Description | How to Get |
|--------|-------------|------------|
| `ZENODO_TOKEN` | Zenodo personal access token | Zenodo → Account Settings → Applications → Personal access tokens → Generate new token with `deposit:write` scope |
| `ZENODO_DEPOSITION_ID` | Concept DOI (the "concept DOI") | After first manual upload via Zenodo web UI, the concept DOI number appears in the URL (e.g., `https://zenodo.org/record/1234567` → `1234567`) |

### Getting Initial Deposition ID

1. Go to https://zenodo.org
2. Click "New Upload"
3. Fill in metadata (title, authors, description, etc.)
4. Upload any file (can be a placeholder)
5. Publish
6. The record ID from the URL (`/record/NNNNN`) is your initial deposition ID
7. From then on, the action creates new versions of this deposition

**Alternative**: Use the Zenodo API directly:
```bash
curl -X POST https://zenodo.io/api/deposit/depositions \
  -H "Authorization: Bearer $ZENODO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

### Node.js 16 EOL Risk

The action uses `runs.using: 'node16'` in its `action.yml`. Node.js 16 reached EOL on 2023-09-11. GitHub has been progressively warning about this and will eventually stop supporting Node 16 actions.

**Current status (as of mid-2026):**
- GitHub has been issuing deprecation warnings for Node 16 actions since late 2024
- Node 16 actions still run but with warnings
- Node 20 is now the minimum recommended runtime

**Mitigation options:**
1. **Fork and update**: Fork the repo, change `runs.using: 'node20'` in `action.yml`, rebuild `dist/index.js` with Node 20
2. **Use `--force` flag**: Some GitHub Actions can force-run with newer Node via `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION=true` env var (temporary)
3. **Rewrite as custom workflow**: Option B avoids this entirely
4. **Wait for upstream fix**: The action maintainer may update — but the repo appears lightly maintained

### Pros/Cons

| Pros | Cons |
|------|------|
| ✅ Well-tested by the community | ❌ Node.js 16 EOL — will break or need fork |
| ✅ Handles concept DOI versioning automatically | ❌ Downloads source zipball from GitHub (includes source, not just built artifacts) |
| ✅ Uploads all GitHub release assets automatically | ❌ Only sets `title` from `.zenodo.json` — does NOT use full metadata (creators, keywords, references, related_identifiers) |
| ✅ Handles file cleanup of old draft files | ❌ The `update_metadata_files` feature is designed for projects that DON'T have a build pipeline — redundant for us |
| ✅ Minimal workflow YAML needed | ❌ Assumes CITATION.cff DOI is in `identifiers[0]` — fragile |
| ✅ Output includes DOI for downstream use | ❌ Calls `process.exit(1)` instead of `core.setFailed()` — poor error handling |
| | ❌ Uses deprecated Zenodo API endpoint (`/api/deposit/depositions/`) |
| | ❌ `upload_type` not set from `.zenodo.json` — Zenodo defaults to "dataset" |

## Option B: Custom Workflow (~50 lines)

### Zenodo REST API Workflow

```yaml
name: Upload to Zenodo

on:
  release:
    types: [published]

permissions:
  contents: read

jobs:
  upload-to-zenodo:
    runs-on: ubuntu-latest
    steps:
      - name: Download release assets
        uses: actions/download-artifact@v4
        with:
          path: release-assets

      - name: Download source zip
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh release download "${{ github.event.release.tag_name }}" \
            --repo "${{ github.repository }}" \
            --pattern "*.zip" \
            --dir release-assets/source

      - name: Upload to Zenodo
        env:
          ZENODO_TOKEN: ${{ secrets.ZENODO_TOKEN }}
          ZENODO_DEPOSITION_ID: ${{ secrets.ZENODO_DEPOSITION_ID }}
          ZENODO_URL: https://zenodo.org
        run: |
          set -euo pipefail

          # ── 1. Create new version of existing deposition ──
          NEW_DEPOSITION=$(curl -sf -X POST \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            "${ZENODO_URL}/api/deposit/depositions/${ZENODO_DEPOSITION_ID}/actions/newversion" \
            | jq -r '.links.latest_draft')
          
          DRAFT_ID=$(echo "$NEW_DEPOSITION" | grep -oP '\d+$')
          echo "Created draft deposition: $DRAFT_ID"

          # ── 2. Get bucket URL for file uploads ──
          BUCKET_URL=$(curl -sf \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}" \
            | jq -r '.links.bucket')

          # ── 3. Clear existing files from draft ──
          EXISTING_FILES=$(curl -sf \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}" \
            | jq -r '.files[].id')
          
          for FILE_ID in $EXISTING_FILES; do
            curl -sf -X DELETE \
              -H "Authorization: Bearer $ZENODO_TOKEN" \
              "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}/files/${FILE_ID}"
          done

          # ── 4. Upload source zip ──
          SOURCE_ZIP=$(find release-assets/source -name "*.zip" | head -1)
          curl -sf -X PUT \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            -H "Content-Type: application/octet-stream" \
            --data-binary "@${SOURCE_ZIP}" \
            "${BUCKET_URL}/$(basename "$SOURCE_ZIP")"

          # ── 5. Upload release assets (PDF, checksums) ──
          find release-assets -not -path "*/source/*" -type f | while read -r FILE; do
            FILENAME=$(basename "$FILE")
            echo "Uploading $FILENAME..."
            curl -sf -X PUT \
              -H "Authorization: Bearer $ZENODO_TOKEN" \
              -H "Content-Type: application/octet-stream" \
              --data-binary "@${FILE}" \
              "${BUCKET_URL}/${FILENAME}"
          done

          # ── 6. Set metadata from .zenodo.json ──
          # Checkout repo to get .zenodo.json
          git clone --depth 1 "https://x-access-token:${GITHUB_TOKEN}@github.com/${{ github.repository }}.git" /tmp/repo
          
          METADATA=$(jq -n --slurpfile zenodo /tmp/repo/.zenodo.json '{
            metadata: $zenodo[0]
          }')
          
          # Override publication_date with today (Zenodo format)
          METADATA=$(echo "$METADATA" | jq \
            --arg date "$(date -u +%Y-%m-%d)" \
            '.metadata.publication_date = $date')
          
          curl -sf -X PUT \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            -H "Content-Type: application/json" \
            -d "$METADATA" \
            "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}"

          # ── 7. Publish ──
          curl -sf -X POST \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}/actions/publish"

          # ── 8. Get the published DOI ──
          DOI_URL=$(curl -sf \
            -H "Authorization: Bearer $ZENODO_TOKEN" \
            "${ZENODO_URL}/api/deposit/depositions/${DRAFT_ID}" \
            | jq -r '.doi_url')
          
          echo "Published to Zenodo: $DOI_URL"
          echo "doi=$DOI_URL" >> "$GITHUB_OUTPUT"
```

### How Concept DOI Versioning Works with curl

Zenodo's concept DOI system:

1. **Initial deposit** (manual or via API) creates record `1234567` with DOI `10.5281/zenodo.1234567`
2. **Concept DOI** is the permanent identifier for the software, e.g., `10.5281/zenodo.1234567`
3. **New version** via `POST /api/deposit/depositions/{concept_id}/actions/newversion`:
   - Creates a new draft with a new record ID (e.g., `1234568`)
   - The new record inherits all metadata from the previous version
   - Both records point to the same concept DOI
   - The version-specific DOI is `10.5281/zenodo.1234568`
4. **After publishing**, the concept DOI resolves to the latest version

The `ZENODO_DEPOSITION_ID` secret should be the **concept record ID** (the original one), not the latest version. The API's `newversion` action always takes the concept record ID and returns the latest draft.

### Pros/Cons

| Pros | Cons |
|------|------|
| ✅ No external action dependency — fully self-contained | ❌ Must be written and maintained |
| ✅ Uses `.zenodo.json` directly — full metadata (creators, keywords, references, related_identifiers, upload_type, etc.) | ❌ No automatic retry logic (need `--retry` or wrapper) |
| ✅ Node.js version irrelevant (pure shell + curl + jq) | ❌ Error handling is basic (curl -sf) |
| ✅ Full control over upload order, metadata, publishing | ❌ Must handle edge cases (draft cleanup, concurrent builds) |
| ✅ Can upload only specific files (not forced to include source zip) | ❌ jq dependency on runner (pre-installed on ubuntu-latest) |
| ✅ `.zenodo.json` already generated by `citation.ts` | ❌ No DOI output as GitHub Action output (would need separate step) |
| ✅ Minimal — ~50 lines, easy to audit | |
| ✅ Runs on ubuntu-latest forever — no runtime deprecation risk | |
| ✅ `upload_type: "software"` correctly set in `.zenodo.json` | |

## Impact on release-it

### Can release-it Still Handle Version Bump + Git Tag + GitHub Release?

**Yes, absolutely.** The Zenodo GitHub Action is completely independent of release-it.

| Concern | Answer |
|---------|--------|
| Does the GH Action replace release-it? | **No.** They serve different purposes: release-it handles versioning + GitHub release; the GH Action handles Zenodo upload. |
| Can they coexist? | **Yes.** The GH Action triggers on `release: published`, which fires AFTER release-it creates the GitHub release. |
| What about `after:bump` hooks? | **Unchanged.** The hooks (`generate:figures`, `build.ts`) run during release-it's local execution, before the GitHub release is created. |
| Does the GH Action need the version number? | **No.** It reads `.zenodo.json` (which `build.ts` already wrote with the correct version) from the repo. |
| Will the GH Action re-upload old assets? | **No.** It triggers only on `release: published`, which fires once per release. |

### Release Flow Diagram

```
Developer runs: pnpm run release
  │
  ├─ release-it: version bump (package.json, CITATION.cff, pyproject.toml)
  │
  ├─ after:bump hooks:
  │   ├─ generate:figures
  │   └─ build.ts → syncs .zenodo.json, compiles PDF, generates checksums
  │
  ├─ release-it: git commit + tag + push
  │
  ├─ release-it: GitHub release created with PDF + checksums
  │
  └─ GitHub Actions: release:published fires
      └─ Zenodo workflow:
          ├─ Create new deposition version
          ├─ Upload source zip + PDF + checksums
          ├─ Set metadata from .zenodo.json
          └─ Publish → get DOI
```

### The `.zenodo.json` as Bridge

The `.zenodo.json` file serves as the bridge between the two systems:

1. **release-it** → `build.ts` → `citation.ts` generates `.zenodo.json` with full metadata
2. `.zenodo.json` is committed to the repo by release-it's git push
3. **Zenodo workflow** reads `.zenodo.json` from the repo and sends it as deposition metadata

This means the custom workflow (Option B) is a **perfect fit** — it was designed to consume exactly the file our build pipeline already produces.

## Recommendation

### Recommended Approach: Option B (Custom Workflow)

**Rationale:**

1. **Perfect metadata alignment**: Our `citation.ts` already generates a comprehensive `.zenodo.json` with all fields Zenodo supports (creators with ORCIDs, keywords, references, related_identifiers, upload_type: "software"). The megasanjay action ignores all of this and only uses `title`.

2. **No Node.js 16 EOL risk**: Pure shell + curl + jq. Will run indefinitely on ubuntu-latest.

3. **No external dependency**: No fork maintenance burden. The workflow is self-contained and auditable in ~60 lines.

4. **Correct `upload_type`**: Our `.zenodo.json` sets `"upload_type": "software"`. The megasanjay action doesn't set this, so Zenodo defaults to "dataset".

5. **Full metadata control**: We can set all fields from `.zenodo.json` in a single PUT request, including the 20+ references and 7 related_identifiers with DOIs.

6. **The `.zenodo.json` bridge already exists**: The build pipeline was designed with this in mind.

### Migration Steps

#### Phase 1: Setup (One-time)

1. **Create initial Zenodo deposition** (manual, via web UI):
   - Go to https://zenodo.org → "New Upload"
   - Upload any file as a placeholder
   - Fill in basic metadata
   - Publish
   - Note the record ID from the URL

2. **Generate Zenodo token**:
   - Go to https://zenodo.org → Account Settings → Applications → Personal access tokens
   - Create token with `deposit:write` scope

3. **Add GitHub secrets**:
   ```
   ZENODO_TOKEN=<your-token>
   ZENODO_DEPOSITION_ID=<record-id-from-step-1>
   ```

4. **Remove old webhook** (if still active):
   - Go to GitHub repo → Settings → Webhooks
   - Delete the Zenodo webhook
   - This prevents double-publishing during transition

#### Phase 2: Create Workflow

5. **Create `.github/workflows/zenodo-upload.yml`** with the Option B workflow above

6. **Test with sandbox first** (optional but recommended):
   - Change `ZENODO_URL` to `https://sandbox.zenodo.org`
   - Create a test deposition on sandbox
   - Verify upload + metadata + publish
   - Switch to production URL

#### Phase 3: Validate

7. **Run a test release**:
   ```bash
   pnpm run release:dry-run   # Verify build pipeline still works
   pnpm run release           # Full release
   ```

8. **Verify Zenodo record**:
   - Check that the new version appears on Zenodo
   - Verify all files are uploaded (source zip, PDF, checksums)
   - Verify metadata matches `.zenodo.json` (creators, keywords, references)
   - Verify concept DOI resolves to latest version

9. **Update CITATION.cff** with the Zenodo DOI:
   - After first successful upload, update the `identifiers` section in `CITATION.cff`:
     ```yaml
     identifiers:
       - type: doi
         value: "10.5281/zenodo.XXXXXXX"  # version-specific DOI
         description: Zenodo version-specific DOI
       - type: doi
         value: "10.5281/zenodo.YYYYYYY"  # concept DOI
         description: Zenodo concept DOI (always resolves to latest)
     ```
   - Commit this change to `main`

#### Phase 4: Optional Enhancements

10. **Add DOI output to workflow** (for downstream use):
    ```yaml
    outputs:
      doi:
        description: 'Zenodo DOI of the published version'
        value: ${{ jobs.upload-to-zenodo.outputs.doi }}
    ```

11. **Add retry logic** (for transient failures):
    ```bash
    # Wrap curl calls with retry
    curl --retry 3 --retry-delay 5 -sf ...
    ```

12. **Add notification** (optional):
    ```yaml
    - name: Comment DOI on release
      if: success()
      uses: actions/github-script@v7
      with:
        script: |
          github.rest.issues.createComment({
            issue_number: context.issue.number,
            owner: context.repo.owner,
            repo: context.repo.repo,
            body: `📚 Published to Zenodo: ${{ steps.upload.outputs.doi }}`
          })
    ```

## Appendix A: Zenodo API Reference (Key Endpoints)

| Method | Endpoint | Purpose |
|--------|----------|---------|
| `POST` | `/api/deposit/depositions` | Create new empty deposition |
| `POST` | `/api/deposit/depositions/{id}/actions/newversion` | Create new version from concept DOI |
| `GET` | `/api/deposit/depositions/{id}` | Get deposition metadata + files |
| `PUT` | `/api/deposit/depositions/{id}` | Update deposition metadata |
| `DELETE` | `/api/deposit/depositions/{id}/files/{fid}` | Remove file from draft |
| `PUT` | `{bucket_url}/{filename}` | Upload file to bucket |
| `POST` | `/api/deposit/depositions/{id}/actions/publish` | Publish deposition |

All endpoints require `Authorization: Bearer {token}` header.
